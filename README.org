#+title: jb-kotlin-lsp-dap.el

Emacs integration for [[https://github.com/Kotlin/kotlin-lsp][JetBrains Kotlin LSP]], using =lsp-mode= and =dap-mode=.
It registers the language client and uses the debug adapter embedded in the
language server.  This is an initial implementation targeting the current
upstream extension protocol, not the separate fwcd Kotlin language server.

* Setup

Install Emacs 28.1 or newer, =lsp-mode=, =dap-mode=, and either =kotlin-mode=
or =kotlin-ts-mode=.  Install the standalone server following the
[[https://github.com/Kotlin/kotlin-lsp#install-kotlin-lsp-cli][upstream instructions]], and make =kotlin-lsp= available on Emacs's =exec-path=.
Complete any first-run setup required by your server distribution separately.

#+begin_src emacs-lisp
(add-to-list 'load-path "~/code/jb-kotlin-lsp-dap.el")
(require 'jb-kotlin-lsp-dap)
(require 'dap-ui)

;; If the server is not on PATH:
;; (setq jb-kotlin-server-command
;;       '("/path/to/kotlin-lsp.sh" "--stdio"))

(add-hook 'kotlin-mode-hook #'lsp-deferred)
(add-hook 'kotlin-ts-mode-hook #'lsp-deferred)
(setq lsp-lens-enable t)
(dap-auto-configure-mode 1)
#+end_src

Open a Kotlin file in a project and let the server finish importing it.
The client ID is =jb-kotlin=; its priority is higher than lsp-mode's bundled
=kotlin-ls= client.  If you set =lsp-enabled-clients= yourself, include
=jb-kotlin=.  Restart an existing workspace after changing clients.

Normal completion, diagnostics, navigation, rename, formatting, semantic
tokens and inlay hints use lsp-mode's standard protocol support and settings.
Completion snippets require Yasnippet; otherwise set =lsp-enable-snippet= to
=nil=.  Enable semantic tokens with =lsp-semantic-tokens-enable= if desired.

* Dependency sources

Definitions into library JARs and JDK classes open in read-only buffers, using
the server's =decompile= command. Attached source JARs and JDK source ZIPs use
the same path. Source buffers retain the original =jar:= or =jrt:= URI and
stay attached to their Kotlin workspace. Files are cached separately for each
workspace in temporary directories, removed when this Emacs process exits.
Normal major-mode hooks and syntax highlighting run in these buffers. Calls
to =lsp= or =lsp-deferred= reuse the original workspace without asking to add
the cache directory as a project, including after a major-mode restart.

=jetbrains.navigateToLocation= commands and hover links (such as "Go to Super
Method") are handled locally. When a help buffer has no workspace context and
several Kotlin workspaces are open, a dependency link asks which one to use.
Only that navigation command is accepted from =command:= links.

The installed server may return no hover or further definition information
for binary-only decompiled Java stubs. Attached Java sources do provide hover
navigation links in the integration fixture. See [[file:test/README.org][isolated test instructions]].

* Running and debugging

- =M-x jb-kotlin-debug=: enter a fully qualified main class, such as
  =com.example.MainKt=.  A prefix argument runs without debugging.
- Run/Debug code lenses invoke the same launch path.
- =M-x jb-kotlin-attach=: attach to an existing JVM's JDWP host and port.
- =M-x dap-debug=: choose the Kotlin JVM, Gradle, or attach template.
  Customize the launch template's main class with =dap-debug-edit-template=.
- Use =dap-breakpoint-toggle=, =dap-continue=, =dap-next=, =dap-step-in=,
  and the other standard dap-mode commands during a session.

Save your project files before launching.  The interactive command and lenses
prefer Gradle when the server says Gradle can launch the module.  The adapter
then builds and runs it.  JVM launches resolve and run the server's build
command first, then resolve the JDK, classpath, module path, working directory,
and VM arguments.  A failed build stops the launch.  Build output appears in
=*Kotlin build*=; =C-g= cancels the waiting build and launch.
Set =jb-kotlin-build-before-run= to =nil= to use already compiled JVM classes.

** Project launch.json

- =M-x jb-kotlin-add-launch-configuration=: choose JVM launch, Gradle launch
  or attach. For launches, main classes from the current file's Run/Debug
  lenses are offered as suggestions; you can enter another fully qualified
  class. Choose a console and configuration name.
- =M-x jb-kotlin-open-launch-file=: open =.vscode/launch.json= in the current
  Kotlin workspace, creating a draft when it does not exist.
- =M-x jb-kotlin-validate-launch-file=: check JSON syntax, required Kotlin
  fields, console names, JDWP ports and argument arrays in the current draft.

Review and save with =C-x C-s=, then use =M-x dap-debug= and select the saved
configuration. Existing entries, comments and trailing commas are preserved
when adding an entry; duplicate names and malformed files are rejected.
Generated source and working-directory paths use =${workspaceFolder}=.
The tools use an already-running Kotlin workspace without asking to register
another project. Debugging can also start from that workspace's launch.json.

For example:

#+begin_src json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "App",
      "type": "intellij_gradle",
      "request": "launch",
      "mainClass": "demo.MainKt",
      "file": "${workspaceFolder}/src/main/kotlin/demo/Main.kt",
      "cwd": "${workspaceFolder}",
      "console": "integratedTerminal",
      "args": ["hello world"],
      "env": {"APP_ENV": "development"}
    }
  ]
}
#+end_src

Use =intellij_jvm= for a plain JVM launch, including Maven projects. Optional
=vmArgs=, =classPaths= and =modulePaths= are arrays of strings. Gradle accepts
=projectPath=, =sourceSet= and =gradleArgs=; set =noDebug= to true for a saved
run configuration. Runtime paths and adapter ports are resolved at launch and
are not written into the generated file.

The generated configuration defaults to =integratedTerminal=. Kotlin launches
use an Emacs comint buffer: type input and press RET, with output retained
when the program ends. Arguments are passed directly without shell expansion;
the adapter's environment additions/removals apply only to that process.
Terminal processes started for a session are cleaned up when it terminates.
External terminals continue through dap-mode's terminal settings.

** Lisp templates

An explicit JVM template:

#+begin_src emacs-lisp
(dap-register-debug-template
 "My Kotlin app"
 '(:type "intellij_jvm"
   :request "launch"
   :name "My Kotlin app"
   :mainClass "com.example.MainKt"
   :file "${workspaceFolder}/src/main/kotlin/com/example/Main.kt"
   :args ["example"]
   :vmArgs ["-Xmx1g"]))
#+end_src

Supported adapter types are =intellij_jvm=, =intellij_gradle= and the legacy
alias =intellij_debugger=.  Gradle configurations also accept =:projectPath=,
=:sourceSet= and =:gradleArgs=.  Launch output defaults to =internalConsole=
(the adapter starts the process and sends its output to dap-mode).
Interactive stdin is not provided by that console.

The adapter port comes from =start_debug_server=.  It is separate from the
=:port= of a JDWP attach target; the adapter itself connects on localhost.
Keep the LSP workspace running while debugging.  Invoke debug commands from
a source buffer or launch.json inside that workspace.

* Project settings

- =jb-kotlin-default-sdk=: JDK home for symbol resolution.
- =jb-kotlin-projects=: vector of import entries, for example
  =[(:type "gradle" :path "file:///path/to/project")]=. The path is a URI.
- =jb-kotlin-build-tools=: hash table mapping workspace URIs to build tools.
- =jb-kotlin-request-timeout=: launch/build resolution timeout in seconds.
- =M-x jb-kotlin-reload-workspace=: reimport with the current settings.
- =M-x jb-kotlin-import-status=: workspace status, folder results and recovery actions.
- =M-x jb-kotlin-show-import-log=: the current workspace's read-only import log.
- =M-x jb-kotlin-retry-import=: retry the import, reopening build-tool selection if blocked.

Kotlin buffers show import progress, readiness, failure or a blocked build-tool
choice in the mode line. Each workspace has its own status and log. Failed
imports display their log without selecting its window; set
=jb-kotlin-show-import-log-on-error= to =nil= to disable this automatic display.
In log and status buffers, press =r= to retry, =l= for the log, or =g= for status.
Retrying from these buffers preserves the workspace's last import settings;
use =jb-kotlin-reload-workspace= in a project buffer to apply changed settings.

Both =intellij/importLog= outcome flags and =intellij/workspaceImportState=
folder results are honored. =intellij/workspaceImportStatus= supplies blocked
build-tool choices. A successful reload response alone does not clear a build
failure. Older servers without the status-query method still report log events.

Saving =pom.xml=, =build.gradle[.kts]= or =settings.gradle[.kts]= automatically
reimports the owning Kotlin workspace. Bazel descriptors (=BUILD=,
=BUILD.bazel=, =MODULE.bazel=, =WORKSPACE[.bazel]=, =.bazelproject= and =*.bzl=)
are supported too. Build buffers do not need to run LSP. Files outside a
running Kotlin workspace do not trigger imports or project prompts.

Set =jb-kotlin-reload-on-save= to =always= (the default), =prompt= or =never=.
=never= leaves client-triggered reloads to =M-x jb-kotlin-reload-workspace=,
which also works in build-file buffers. Set =jb-kotlin-reload-delay= to change
the idle delay (default one second). Rapid saves share a reload; saves during
an outstanding request queue one subsequent reload. Imports run asynchronously.
Request failures are reported with a manual retry command.

Files already handled by server-side import watchers, such as =workspace.json=,
are deliberately excluded. The client policy does not disable those watchers.
External file changes and other build inputs (such as Gradle version catalogs)
are not covered by this save hook; use the manual reload command for those.

* What the VS Code client advertises

The implementation was checked against upstream commit
=a18d1716202a742719acf30354dc01cc27b9b5e8= on 2026-09-16.
The extension delegates standard LSP capabilities to =vscode-languageclient=;
this package delegates them to =lsp-mode= rather than claiming VS Code's
entire capability set.  The additional feature switches below are fields of
=initialize.initializationOptions=, not =capabilities.experimental=.

| Option               | This package | Meaning                                                   |
|----------------------+--------------+-----------------------------------------------------------|
| =lazyIntentions=     | true         | Execute a quick fix only when its command is selected      |
| =runMainCodeLens=    | true         | Handle =intellij.jvm.runMain= on the client                 |
| =intellijExtensions= | true         | Custom IntelliJ editor UI notifications/refactoring dialogs |
| =defaultSdk=         | if set       | JDK used for symbol resolution                             |
| =projects=           | vector       | Explicit project import entries                            |
| =buildTools=         | object       | Workspace URI to build tool mapping                        |

The =intellijExtensions= opt-in enables server-requested clipboard copies,
action menus, rename, completion and parameter hints. Actions use the normal
=lsp-execute-code-action= entry point; nested choices appear in the minibuffer.
Only the three supported editor commands are mapped to Emacs commands.

To try a verified rename interaction, put this in a Kotlin project:

#+begin_src kotlin
fun demo() {
    when (System.currentTimeMillis()) {
        0L -> System.out.println("zero")
        1L -> System.out.println("one")
        else -> System.out.println("other")
    }
}
#+end_src

Place point on =when=, run =M-x lsp-execute-code-action= and select
=Replace 'when' with 'if'=. The server introduces a local variable and asks
Emacs to rename it. This example needs =when= as a standalone statement;
=return when (...)= and expression-bodied functions follow a different path.
Ordinary symbol rename is =M-x lsp-rename= and need not appear as a code action.

This branch already enables =intellijExtensions=. Start a fresh =just run=
instance after updating the library. Existing LSP connections keep the flags
sent at initialization; after loading updated Lisp, =lsp-workspace-restart=
renegotiates them. Editor prompts are deferred until the initiating action
returns, avoiding nested synchronous requests in lsp-mode.

When a refactoring reports conflicts, a read-only review buffer shows messages
and clickable source locations. Select Continue (or press =c= in that buffer)
to proceed, or Cancel (=q= or =C-g=) to stop. Closing or hiding the review,
editing any file buffer, server cancellation or disconnect cancels the pending
refactoring. Continuing rechecks buffer contents and conflict files on disk.
Opening a source location keeps the review available.

Server support varies: the installed 263.4702.0-EAP supports clipboard and
rename notifications, but predates =intellij/showConflicts=. The client handles
that protocol for newer servers; see [[file:test/README.org][validation details]].
See [[file:GAPS.org][the implementation queue]] for remaining gaps. Remote/TRAMP server
operation and Windows build wrappers are not supported. Test explorer parity
with the pinned VS Code extension has not been established.

Protocol sources (pinned for reproducibility):

- [[https://github.com/Kotlin/kotlin-lsp/blob/a18d1716202a742719acf30354dc01cc27b9b5e8/vscode-extension-core/src/dap.ts][dap.ts]]: adapter startup, lens option, launch resolution and field mapping.
- [[https://github.com/Kotlin/kotlin-lsp/blob/a18d1716202a742719acf30354dc01cc27b9b5e8/vscode-extension-core/src/intellijExtensions.ts][intellijExtensions.ts]]: custom UI protocol and lazy intentions.
- [[https://github.com/Kotlin/kotlin-lsp/blob/a18d1716202a742719acf30354dc01cc27b9b5e8/vscode-extension-core/src/lspClient.ts][lspClient.ts]]: stdio startup and initialization settings.
- [[https://github.com/Kotlin/kotlin-lsp/blob/a18d1716202a742719acf30354dc01cc27b9b5e8/vscode-extension-core/src/buildTask.ts][buildTask.ts]]: build command resolution.

Older server releases may lack these commands.  Errors from the server are
reported rather than falling back to obsolete launch-resolution protocols.

* Development

Run =just run= from this checkout to start Emacs with your normal configuration
and require =jb-kotlin-lsp-dap= from this directory.

#+begin_src sh
just run
just run /path/to/project/src/main/kotlin/Main.kt
just run -nw
EMACS=/path/to/emacs just run
#+end_src

Extra arguments are passed to Emacs.

With lsp-mode and dap-mode on the batch Emacs load path:

#+begin_src sh
emacs --batch -L . -l test/jb-kotlin-test.el -f ert-run-tests-batch-and-exit
emacs --batch -L . --eval '(setq byte-compile-error-on-warn t)' \
  -f batch-byte-compile jb-kotlin-navigation.el jb-kotlin-reload.el jb-kotlin-import.el jb-kotlin-refactor.el jb-kotlin-launch.el jb-kotlin-terminal.el jb-kotlin-lsp-dap.el
#+end_src

The same checks are available as =make test= and =make compile=.  Use
=-L /path/to/dependency= arguments if your dependencies are only made available
by your interactive init file.  Batch Emacs does not load that init file.
Tests exercise protocol requests, code lens dispatch, JVM/Gradle field
mapping, attach ports, and real build process exit handling.  They do not
require a running language server or download dependencies.

Prefer =integratedTerminal= for Gradle: this server sometimes ends an
internalConsole debug session before delivering final program output.

dap-mode currently ignores the server's =invalidated= refresh notification.
The live test explicitly re-requests values, so automatic locals/watch UI
refresh remains a documented gap. External terminals are not live-tested.
