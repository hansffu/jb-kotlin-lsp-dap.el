#+title: Isolated Kotlin client tests

Unit tests: =emacs --batch -L . -l test/jb-kotlin-test.el -f ert-run-tests-batch-and-exit=.
Batch Emacs does not load the user's init. Dependencies must be on its load-path.

* Dependency navigation integration test

Requires Python 3, JDK 17+ (javac), kotlin-lsp, lsp-mode and dap-mode.
The generator creates two standalone JSON-import projects: a compiled library
without attached sources, and the same library with an attached source JAR.
The library is built locally, with no dependency downloads. Project directories
and every test Emacs/LSP state directory live under the supplied new directory.

#+begin_src sh
python3 test/create-navigation-projects.py /tmp/jb-navigation-test
JB_KOTLIN_TEST_ROOT=/tmp/jb-navigation-test JB_KOTLIN_TEST_PROJECT=binary \
  emacs --batch -L . -l test/navigation-smoke.el
JB_KOTLIN_TEST_ROOT=/tmp/jb-navigation-test JB_KOTLIN_TEST_PROJECT=sources \
  emacs --batch -L . -l test/navigation-smoke.el
#+end_src

Always use a new Emacs process; never use emacsclient or the user's existing
server. Each test starts its own stdio language server with private cache,
config, log, Java preferences and LSP-session paths, and shuts down only that
server. The test prints both process IDs. Existing server licensing/first-run setup must already
be satisfied; the harness does not accept terms or change license settings.

The test checks real Kotlin definition results into the JAR and JDK, read-only
source buffers, original URI preservation, subsequent hover requests, xref
conversion, source reopening, command links and explicit JRT decompilation.
Java source checks also cover syntax highlighting, major-mode restart and
=lsp-deferred= mode hooks, with any project-discovery attempt failing the test.
For attached Java sources it follows a real server-generated "Go to Super
Method" hover link. Binary-stub hover/definition results may be empty on the
installed server; the test records these and compares direct requests before
and after opening the source buffer instead of claiming those results exist.
The test major mode supplies only the Kotlin language ID; it does not assess
kotlin-mode/kotlin-ts-mode indentation or syntax highlighting.

* Build-file reload integration test

Create Gradle Groovy and Kotlin DSL projects using an existing Gradle 9.x
distribution. The generator packages it into a local wrapper ZIP; no Gradle
distribution or plugin downloads are needed. Both projects use Gradle's Java
plugin and Kotlin source in a Java source root, avoiding a Kotlin plugin download.

#+begin_src sh
python3 test/create-reload-projects.py /tmp/jb-reload-test \
  --gradle-home /path/to/gradle-9.3.1
JB_KOTLIN_TEST_ROOT=/tmp/jb-reload-test JB_KOTLIN_TEST_PROJECT=groovy \
  emacs --batch -L . -l test/reload-smoke.el
JB_KOTLIN_TEST_ROOT=/tmp/jb-reload-test JB_KOTLIN_TEST_PROJECT=kotlin \
  emacs --batch -L . -l test/reload-smoke.el
#+end_src

Each run uses a separate Emacs/LSP process and a private Gradle user home.
Gradle needs local sockets for its daemon, so a sandbox that blocks sockets
cannot run this test. The fixture configures its daemon to exit after ten idle
seconds. The user's Emacs server and build caches are not used.

The test saves the build file to add a local JAR, verifies its class becomes
resolvable, removes it via another save, and verifies it becomes unresolved.
It checks that precisely two reload requests were sent and that build buffers
do not need LSP. Batch Emacs has no idle command loop, so the test explicitly
fires the queued idle callback; save hooks and all server requests are real.
Unit tests cover policies, coalescing, saves during requests, nested workspaces,
failures, disconnects and exclusion of server-watched settings. Maven/Bazel
descriptor routing is unit-tested; their imports are not covered by this fixture.

Validated on 2026-09-17 with Emacs 31.1, Kotlin LSP 263.4702.0-EAP and Gradle
9.3.1: both live fixtures passed; all 34 unit tests passed with plist and
hash-table protocol data; package byte compilation passed with warnings
treated as errors.

* Import status and recovery integration test

Generate a fresh fixture using =create-reload-projects.py= as above, then run:

#+begin_src sh
JB_KOTLIN_TEST_ROOT=/tmp/jb-import-test \
  emacs --batch -L . -l test/import-smoke.el
#+end_src

This uses the same isolated Emacs/LSP/Gradle setup and local-socket requirement
as the reload test. It adds a minimal POM alongside Gradle to trigger the real
build-tool chooser, dismisses it, and verifies that retry from the status view
reopens it. After choosing Gradle it saves a deliberately failing build script,
checks the failure and read-only log, fixes the script and retries from the log.
It verifies that the original workspace's settings survive the retry and that
the mode-line indicator recovers to Ready. No Maven import is performed.

Validated on 2026-09-18 with Emacs 31.1, Kotlin LSP 263.4702.0-EAP and Gradle
9.3.1. The live recovery test and all 45 unit tests passed; the latter cover
independent workspaces, JSON false values, partial folder failures, stale
initial snapshots, unsupported status queries and disconnected log views.

* Refactoring UI integration test

#+begin_src sh
python3 test/create-navigation-projects.py /tmp/jb-refactoring-ui-test
JB_KOTLIN_TEST_ROOT=/tmp/jb-refactoring-ui-test \
  emacs --batch -L . -l test/refactor-smoke.el
#+end_src

This reuses the isolated JSON-project setup, with private server state and a
fresh Emacs process. It invokes the real server's =applyModCommand= dispatcher
to generate clipboard and rename notifications. The local rename command is
intercepted to avoid prompting in batch mode; the real navigation/notification
path must reach it. Clipboard testing uses a private kill ring with system
clipboard writes disabled.

A second test exercises server-held edits after Continue, Cancel and intervening
edits. It explicitly skips if the server lacks the ShowConflicts serializer,
as installed 263.4702.0-EAP does. It remains available for newer servers. These
are protocol fixtures, not coverage of every Kotlin refactoring. Unit tests
cover conflict UI lifecycle, asynchronous dispatch, cancellation, stale edits,
location reveal, nested choices and editor-command targeting.

Validated on 2026-09-18 with Emacs 31.1 and Kotlin LSP 263.4702.0-EAP:
59 unit tests passed with both plist and hash-table protocol data; byte
compilation passed with warnings treated as errors. Live clipboard and rename
notifications passed. The live conflict test was skipped for missing server
support; conflict acceptance/cancellation is verified only in client tests.

* Real code action followed by rename

Using the generated navigation fixture from above:

#+begin_src sh
JB_KOTLIN_TEST_ROOT=/tmp/jb-refactoring-ui-test \
  emacs --batch -L . -l test/refactor-actions-smoke.el
#+end_src

This copies [[file:fixtures/refactor/Actions.kt][the Kotlin example]] into the fixture project,
requests the actual action =Replace 'when' with 'if'=, executes the server's
returned command and waits for the server to request rename. It supplies
=timestamp= in place of interactive input, then uses the real =textDocument/rename=
request and verifies the declaration and both references changed. Batch Emacs
has no idle command loop, so the test dispatches the queued editor callback
only after the initiating executeCommand returns. Other LSP timers run normally.

Passed on 2026-09-18 with the installed Kotlin LSP 263.4702.0-EAP, in a separate
Emacs process. This exposed and now covers a timeout caused by starting rename
inside the original synchronous code-action request.

* Launch configuration and debugging integration tests

The generator needs a local Gradle distribution and a populated Maven
repository containing Kotlin 2.2.21, kotlin-maven-plugin and its dependencies,
plus the pinned Maven build plugins. It copies that repository into the new
test root (potentially several GB); it does not modify the original repository.
Missing stdlib source/javadoc attachments can be fetched into the private copy
with the optional =--download-missing-docs= flag. All subsequent builds/imports
use that private repository offline.

#+begin_src sh
python3 test/create-debug-projects.py /tmp/jb-debug-test \
  --gradle-home /path/to/gradle-9.3.1 \
  --maven-repository "$HOME/.m2/repository" --download-missing-docs
JB_KOTLIN_TEST_ROOT=/tmp/jb-debug-test JB_KOTLIN_TEST_PROJECT=gradle \
  emacs --batch -L . -l test/debug-smoke.el
JB_KOTLIN_TEST_ROOT=/tmp/jb-debug-test JB_KOTLIN_TEST_PROJECT=maven \
  emacs --batch -L . -l test/debug-smoke.el
#+end_src

Run these only in new Emacs processes. Each uses private Emacs/LSP state,
breakpoint persistence, server caches, Java preferences and Gradle user home.
Local sockets are required for Gradle, DAP and JDWP. Import uses the packaged
Gradle distribution; launch uses the =gradle= executable on PATH. The Gradle
fixture invokes the cached Kotlin compiler through a custom JavaExec task;
it does not verify Kotlin Gradle plugin integration. The Maven fixture uses
the normal Kotlin Maven plugin. =mvn= and =gradle= must be on PATH.

Both tests wait for indexing, generate a portable launch.json and parse it
through dap-mode, hit a real source breakpoint, inspect locals, evaluate an
argument, step and continue. They then run without debugging in the integrated
console, verify environment/argv and send stdin, and finally attach to a
separate suspended JVM on an ephemeral port and repeat breakpoint checks.
Session processes are cleaned up and LSP traces remain in each state directory.
The batch test explicitly retries delayed variable values; it does not verify
automatic locals/watch UI refresh. External terminals are not exercised.

Validated on 2026-09-18: both live projects passed with Emacs 31.1, Kotlin LSP
263.4702.0-EAP, Java 25, Kotlin 2.2.21, Gradle 9.3.1 import / 9.7.1 launch.
All 70 client tests passed with plist and hash-table LSP data; compilation
passed with warnings treated as errors. Client tests additionally cover
JSONC preservation, malformed/duplicate configurations, unsaved wizard drafts,
workspace lookup, literal argv, environment removal and session-owned cleanup.

Known server/client limits: Gradle internalConsole can miss final program
stdout when the adapter terminates; integratedTerminal retained it in these
tests. The adapter emits =invalidated= for delayed variable values but dap-mode
has no handler, so the UI may need a manual refresh. These remain in GAPS.org.
